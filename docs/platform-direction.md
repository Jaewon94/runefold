# 플랫폼 방향 검토: 웹 게임 우선, 안 되면 Steam 네이티브 (2026-10-27)

사용자 의견(2026-10-27): "웹 게임으로 해도 상관없나? 나중에 도집사에 붙일까도 생각 중", "웹 게임이지만 퀄리티 있는 웹 게임, 안 되면 기존 하던 것".
이 문서는 계획 문서다. **결정이 아니라 검토**이며 결정 장부 DEC50 은 "대기"다. 정본은 Confluence 에 둔다.

## 1. 현재 결정과의 관계
- RUNE-DEC01 은 "Steam 출시용 네이티브 PC 게임(웹 게임 아님)"이었다. 이 방향은 아직 바뀌지 않았고, 웹을 우선 검토한다는 뜻을 DEC50(대기)에 적었다.
- 같은 Godot 프로젝트에서 웹 빌드와 Windows 빌드를 둘 다 내보낼 수 있다. 그래서 "웹을 먼저 시도하고 안 되면 Steam 네이티브"는 **버리는 작업이 거의 없는 순서**다. 단, 코드를 두 플랫폼에서 돌아가게 짜는 비용(아래 4절)이 생긴다.

## 2. Godot 4 웹 내보내기의 제약 (공식 문서 확인, 2026-10-27, https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html)
| 항목 | 내용 | 우리에게 |
|---|---|---|
| 렌더러 | WebAssembly 와 WebGL 2.0 필요, Compatibility 렌더러만 지원 | 프로젝트가 이미 gl_compatibility 라 맞음 |
| 언어 | C# 프로젝트는 웹 내보내기 불가 | GDScript 라 해당 없음 |
| 스레드 | 단일 스레드 내보내기가 4.3 부터 기본. 헤더(COOP/COEP) 요구가 없다. 대신 멀티스레드보다 느림 | 턴제 2D 라 문제 가능성 낮음(실측 필요) |
| GDExtension | 웹용으로 따로 컴파일해야 동작 | **GodotSteam 은 웹에서 못 쓴다**(별도 계층 필요, 4절) |
| 오디오 | 기본 재생에는 이펙트·실시간 합성 제한. 브라우저가 자동재생을 막아 클릭 뒤에 시작해야 함 | 시작 화면에 클릭 필요 |
| 저장 | `user://` 는 IndexedDB. 쿠키를 막거나 시크릿 모드면 저장이 안 됨 | 저장 설계에 영향(도집사 서버 저장이 대안) |
| iframe 삽입 | 가능. 단, 서드파티 쿠키가 켜져 있어야 저장이 된다 | 도집사에 삽입할 때 영향 |
| 브라우저 | Safari 는 WebGL 2.0 문제가 있어 크롬 계열·Firefox 권장 | 지원 브라우저 범위 결정 필요 |
| 백그라운드 탭 | 탭이 백그라운드면 멈춘다 | 턴제라 영향 적음 |
| 성능 | WebAssembly 는 네이티브보다 느리다. 모바일은 더 불리 | 실측 필요 |

## 3. 실측 (2026-10-27, 시험용 내보내기, 시험 결과는 버림)
- 현재 뼈대 프로젝트의 단일 스레드 웹 내보내기가 **성공**했다.
- `index.wasm` 39.5MB(원본), gzip 압축 약 10MB. 게임 데이터(`index.pck`)는 아직 5.5KB. 엔진 본체가 대부분이라 에셋이 늘면 pck 가 커진다.
- 로컬 서버에서 `.wasm` 이 `application/wasm` 으로 제공됨을 확인했다.
- **브라우저에서 실제로 실행하는 확인은 하지 못했다**(NOT RUN, Chrome 확장 연결이 안 됨). 로딩 시간, 프레임, 저장은 미확인.

## 4. 웹 우선으로 가려면 설계에 생기는 일
1. **플랫폼 계층 분리:** Steam 기능(업적·클라우드 저장·입력)은 플랫폼 인터페이스 뒤에 두고, 웹 빌드에서는 빈 구현이나 웹 구현(도집사 연동)을 쓴다. 규칙 코어는 이미 엔진·플랫폼과 분리되어 있다(결정론 코어).
2. **저장:** 브라우저 저장(IndexedDB)이 막힐 수 있으므로 서버 저장(도집사) 경로를 옵션으로 설계한다.
3. **입력:** 마우스·키보드 위주. 컨트롤러·Steam Deck 요건은 Steam 경로에서만 필요.
4. **에셋 라이선스:** 웹은 에셋 파일이 사용자 브라우저로 그대로 내려간다. 맞춤 약관 팩의 "재배포 금지"가 웹 서비스 번들에 해당하는지 작가 확인이 필요하다(Steam 번들보다 파일이 더 쉽게 노출).
5. **수익 구조:** 완성 게임을 무료 웹으로 열면 Steam 판매와 겹친다. 웹은 데모·무료판·도집사 내부용 중 무엇인지 정해야 한다.
6. **품질 기준:** "퀄리티 있는 웹 게임"의 기준을 숫자로 정한다(첫 로딩 시간, 프레임, 저장 안정성, 지원 브라우저). 아래 질문에서 사용자가 정한다.

## 5. 사용자에게 필요한 답 (DEC50 을 확정하려면)
1. "도집사에 붙인다"는 정확히 무엇인가? (a) 도집사 화면에 웹 빌드를 iframe 으로 삽입 (b) 도집사 로그인·계정과 연동하고 저장·기록을 서버에 보관 (c) 도집사의 서브서비스로 배포·운영(REA Lab 처럼).
2. 웹 빌드가 **주 제품**인가, **Steam 판매의 데모/보조**인가?
3. Steam 출시는 계속 목표인가, 웹이 성공하면 생략해도 되는가?
4. 외부 사용자가 쓰는 서비스인가, 본인·소수 전용인가? (공개 범위에 따라 개인정보·약관·접속 부하가 달라진다.)
