# Runefold 설계 (초안 v0)

## 한 줄 요약
타일 위에서 소대를 움직이는 전술 전투 + 카드 기반 행동 + 합성 승급 + 유물 빌드의 판타지 로그라이크.

## 참고작과 반영 방식
| 축 | 참고작 | 룬폴드 |
|---|---|---|
| 전투 | XCOM·라피스 | 8×8 안팎 타일 격자, 유닛 3~4명, 한 턴에 이동 + 행동. 엄폐·고저차·사거리 모양, 적 행동 예고 |
| 행동 | 슬레이 더 스파이어 | 유닛별 직업 카드, 매 턴 손패 5장, 공유 에너지 3. 카드가 공격·방어·마법을 정함 |
| 합성 | 아르카나 택틱스 | 야영지에서 같은 유닛 3명 → ★ 승급, 같은 카드 3장 → 단계 승급(합성은 항상 3개 → 1개) |
| 성장 | 슬레이 더 스파이어 | 층 지도(전투/엘리트/상점/이벤트/야영/보스), 보스·저주 유물, 태그 시너지(불꽃·방어·합성·소환) |
| 분위기 | 판타지 | 타로식 대비전(Arcana) 세계관. 보스는 타락한 아르카나 |

## 핵심 결정
- 이동은 유닛 스탯으로 공짜, 행동만 카드와 에너지로 제한한다(이동까지 카드로 하면 템포가 느려진다).
- 규칙 엔진은 렌더링과 분리한다. 엔진 API 에 기대지 않는 순수 코드, 시드 고정 난수, 결정론적 시뮬레이션.
  화면 없이 엔진의 헤드리스 시험으로 전투·합성·유물 규칙을 검증한다.

## 합성과 등급
**합성 규칙: 항상 같은 것 3개 → 1개.** 2개 합성은 없다.
- 대상은 유닛과 카드. 이름과 단계가 모두 같은 3개만 합쳐진다(다른 단계·다른 이름은 섞이지 않는다).
- 단계는 1→2→3 (유닛은 ★1~★3, 카드는 Lv1~Lv3). 3단계가 최대이며, 최대까지 가려면 같은 것 9개가 필요하다.
- 합성 결과는 능력치·효과가 오르지만 **등급(희귀도)은 바뀌지 않는다.** 단계와 등급은 별개 축이다.
- 합성 시점은 야영지와 상점 전후의 정리 화면에서 한다. 자동/수동 여부는 미정(아래 미결).
- 유물은 합성하지 않는다.

**등급(희귀도) — 유닛·카드·유물 공통, 4단계**
| 등급 | 색 | 비고 |
|---|---|---|
| 일반 (Common) | 회색 | 가장 흔함, 합성 재료의 주류 |
| 고급 (Uncommon) | 초록 | |
| 희귀 (Rare) | 파랑 | 빌드 핵심 |
| 전설 (Legendary) | 주황 | 보스·특수 보상 위주, 한 판에 1개 안팎 |
유물은 이에 더해 보스 유물과 저주 유물 분류를 둔다. 등급별 출현 확률과 가격은 M3 에서 정한다.

**미결:** 합성 자동/수동 · 소대 정원과 대기석 수 · 전설 유닛 존재 여부 · 합성 단계별 능력치 증가폭.
**합성 빈도:** 3개 합성은 한 판 안에서 같은 것을 3개 모으기 어렵다. 풀을 작게 유지하고, 이미 가진 것이 나올 확률을 높이고, 상점에서 고르거나 살 수 있게 한다. M4 에서 실측한다.

## 직업 (MVP 4종)
기사(방어·도발) · 레인저(원거리·위치) · 마법사(원소 조합) · 성직자(회복·정화). 추후 도적·소환사.

## 한 판
목표 30~45분. 메타 성장은 직업·유물 해금과 난이도 단계.
노드 수는 잠정이다. 격자 전투는 한 판이 슬레이 더 스파이어보다 길어서(전투 3~4분이면 3막 × 12노드는 목표 시간에 안 들어간다) 막당 8~10노드로 줄이거나 전투를 짧게 만든다. M3 시험 플레이에서 실제 시간을 재서 정한다.

## 아트 방향
**2D 도트(픽셀아트), 움직임은 최소.** 턴제라 큰 애니메이션이 필요 없고, 제작 비용과 에셋 수를 줄이는 방향이다.
- 기준 해상도 480×270, 정수 배율(×4 = 1080p, ×8 = 4K)로 확대한다. 타일 16×16 이 잠정 안이며 확정 전이다.
  Steam Deck(1280×800)은 정수 배율이 맞지 않아 별도 대응(레터박스 또는 ×2 확대)이 필요하다.
- 유닛 스프라이트는 대기 2~4프레임이 기본이다. 공격·피격·이동은 별도 프레임 대신 위치 이동(트윈), 흰색 번쩍임,
  화면 흔들림, 간단한 파티클로 표현한다.
- **캐릭터·몬스터의 움직임은 최소로 한다.** 걷기·달리기 프레임은 만들지 않는다. 타일 이동은 대기 프레임 그대로 칸 사이를 미끄러지듯 옮기고,
  공격은 앞으로 살짝 내딛었다 돌아오는 트윈, 피격은 흰색 번쩍임과 밀림, 사망은 페이드아웃으로 처리한다. 직업·몬스터당 필요한 그림은 대기 2~4프레임이 전부다.
- 카드·유물은 정지 아이콘(예: 32×32)으로 제작한다. 일러스트 풀 컷은 쓰지 않는다.
- 직업 4종 × 단계 3(★ 표시는 장식·색조 변화로 구분) 규모로 스프라이트 수를 통제한다.
- 도구 후보는 Aseprite(유료)와 무료 대안(LibreSprite, Pixelorama). 가격·라이선스는 도입 시점에 URL 과 확인일을 남긴다.
- 에셋 라이선스는 받을 때 출처 URL·확인일을 기록한다.

## 목표 플랫폼
Steam 출시용 네이티브 PC 게임(Windows 우선, Steam Deck 고려). 웹 게임이 아니다.
Steamworks 연동(업적·클라우드 저장·Steam 입력)과 Steam 상점 요건(캡슐 이미지·트레일러)이 필요하다.

## 기술안
- **엔진: Godot 4 확정**(2026-10-20 사용자 결정). 정확한 버전과 다운로드 URL 은 설치 시점에 공식 사이트에서 확인하고 이 문서에 확인일과 함께 남긴다.
- Steam 연동은 GodotSteam, 시험은 GUT 또는 GdUnit4, 언어는 GDScript(C# 은 .NET SDK 가 필요해 보류).
- **규칙 엔진은 렌더링과 분리**한다. 엔진 API 에 기대지 않는 순수 코드, 시드 고정 난수, 결정론적 시뮬레이션,
  화면 없이 헤드리스 시험으로 전투·합성·유물 규칙을 검증한다.
- 아트는 2D 도트(위 「아트 방향」). 개발 초기에는 임시 도형으로 시작한다.
  이진 에셋이 늘면 git LFS 도입을 검토한다.

## 개발 환경
- 원격 저장소: GitHub `Jaewon94/runefold`(비공개). 맥 사본은 읽기·문서 수정용, 코드 작업은 Home1 세션이 맡는다.
- 개발 환경은 Home1 의 **게임 전용 Windows 일반 계정 `game`**(관리자 아님)과 그 전용 WSL `game-dev`(Ubuntu 24.04)이다. WSL 은 Windows 드라이브 마운트와 interop 이 꺼져 있고 화면(DISPLAY)이 없다. 구성 중이며 현재 상태는 Confluence 「03 개발 환경」에 둔다.
- 임시로 Home1 `dojipsa` 계정 WSL(`~/games/runefold`)에 작업 사본이 있다. `game` 환경이 끝나면 옮기고 이쪽은 정리한다.
- 개발·헤드리스 시험·Windows 내보내기는 WSL 에서 한다. **플레이 확인은 Home1 모니터에서** 하며, 내보낸 exe 를 모든 계정이 읽을 수 있는 폴더로 복사해 모니터에 로그인된 계정에서 실행한다.
- 회사 자료 경로는 건드리지 않는다. 시스템 설치 없이 사용자 폴더 안 포터블 실행 파일만 쓴다.

## 정본과 관리
- 이슈·문서의 정본은 **Jira `RUNE`(룬폴드)** 와 **Confluence `RUNE` 스페이스**이다(2026-10-20 생성). 이 문서는 Confluence 「01 게임 설계」의 사본이며, 어긋나면 Confluence 쪽이 맞다.
- Jira: 에픽 RUNE-1~7 이 마일스톤 M0~M6 에 대응한다. 흐름은 할 일 → 진행 중 → 완료.
- 참고 게임 분석(REA)은 요약 결론과 링크만 이쪽에 두고, 원본 기록과 상대 게임의 코드·에셋·디컴파일 출력은 올리지 않는다.

## 작업 규칙 (가벼운 버전)
- 브랜치는 `main` + 작업 브랜치. 커밋은 `<type>(<scope>): 한국어 요약`.
- 작업은 Jira `RUNE` 이슈 단위로 한다. 브랜치는 `<type>/RUNE-<n>-<slug>`, 커밋 본문에 `Refs RUNE-n`.
- 원격은 GitHub(비공개)이며 CI 는 나중에 결정한다.
