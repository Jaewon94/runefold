# Runefold 설계 (초안 v0.1)

> 정본: Confluence 01 게임 설계(page 8814593). 이 파일은 사본이며 마지막 동기화는 2026-10-21 이다.

## 한 줄 요약
타일 위에서 소대를 움직이는 전술 전투 + 카드 기반 행동 + 합성 승급 + 유물 빌드의 판타지 로그라이크.

## 참고작과 반영 방식
| 축 | 참고작 | 룬폴드 |
|---|---|---|
| 전투 | XCOM·라피스 | 8×8 고정 타일 격자(고저차 없음), 출전 유닛 4명, 팀 턴, 한 턴에 이동 + 행동. 엄폐·사거리 모양, 확률 명중, 적 행동 예고 |
| 행동 | 슬레이 더 스파이어 | 소대 공유 덱(직업 태그), 매 턴 손패 5장, 공유 에너지 3. 카드가 공격·방어·마법을 정함 |
| 합성 | TFT·Super Auto Pets | 야영지에서 같은 유닛 3명 → ★ 승급, 같은 카드 3장 → 단계 승급(같은 것 승급은 항상 3개 → 1개). 서로 다른 재료는 조합식(레시피)으로 새것을 만든다 |
| 성장 | 슬레이 더 스파이어 | 층 지도(전투/엘리트/상점/이벤트/야영/보스), 보스·저주 유물, 태그 시너지(불꽃·방어·합성·소환) |
| 분위기 | 판타지 | 타로식 대비전(Arcana) 세계관. 보스는 타락한 아르카나 |

## 핵심 결정
- 이동은 유닛 스탯으로 공짜, 행동만 카드와 에너지로 제한한다(이동까지 카드로 하면 템포가 느려진다).
- 규칙 엔진은 렌더링과 분리한다. 엔진 API 에 기대지 않는 순수 코드, 시드 고정 난수, 결정론적 시뮬레이션.
  화면 없이 엔진의 헤드리스 시험으로 전투·합성·유물 규칙을 검증한다.

## M1 전 결정 (2026-10-21, 사용자 결정)
- 격자: 8×8 고정, 고저차 없음. 장애물·엄폐 칸만 둔다.
- 턴: 팀 턴(아군 전원이 행동한 뒤 적 전원이 행동). 이동은 유닛당 한 번이며 행동 카드를 쓰기 전이면 취소할 수 있다(잠정).
- 명중: 확률(XCOM식). 화면에 표시한 확률은 항상 정확해야 한다. 사용자가 추천(확정 명중)과 다르게 선택했으며 종이 프로토타입에서 '빗나가서 억울함'을 우선 검증한다.
- 사망: 전투 중 쓰러진 유닛은 영구 손실. 패배 조건은 전멸로 가정(미확정). 쓰러진 유닛의 직업 카드 처리는 미정이며 종이에서는 「뽑는 즉시 버리고 1장 다시 뽑는다」를 임시로 쓴다. 합성으로 키운 유닛을 확률로 잃을 수 있어 완화 장치(부활·보호 카드 등)를 종이 프로토타입에서 시험한다.
- 덱: 소대 공유 덱 + 직업 태그. 손패 5장·에너지 3을 공유하고 카드를 낼 때 실행 유닛을 고른다(직업 카드는 해당 직업만).
- 정원: 출전 4명 + 대기석 6칸(M3 실측으로 조정 가능, 잠정).
- 스탯: 유닛은 HP·이동력·방어를 가진다. 공격력과 사거리는 카드가 정한다.
- 합성: 승급은 정리 화면에서 플레이어가 확정, 조합식은 서로 다른 재료 2~3개 → 새것(「합성과 등급」 참조).

## 방향: 네오 다크세이버 느낌 강화 (2026-10-21)
- 방향(사용자 결정): 네오 다크세이버(라피스) 느낌을 더 강하게 가져간다. 카드 행동, 로그라이크 구조, 합성·조합식, 유물은 유지한다.
- 틱 차용(일부만, 잠정): 팀 턴이 기본이다. 적 틱 카운터(몇 라운드 뒤 행동할지)와 강한 카드가 사용 유닛의 다음 이동을 늦추는 「지연」은 종이 프로토타입 변형 T 로 시험한 뒤 채택 여부를 정한다. 실시간 진행은 하지 않는다. (네오 다크세이버의 틱은 실시간 게이지이고, 적 카운터는 Wildfrost 의 구조에 가깝다.)
- 지휘관 4인 편성(주 지휘관 1 + 부지휘관 3)과 단 성장(잠정): 승급(★2, ★3)마다 도트 외형이 바뀌고 직업 카드 1장이 덱에 추가되며 HP·방어가 오른다(잠정 제안). 유닛 종류 수 × 3 변형이 필요해 아트 비용이 늘어난다(직업당 1종이면 12). 무료 에셋 단계에서는 색조·장식 변화로 대체한다.
- 시나리오 진행 차용(해석, 잠정): 로그라이크 노드는 그대로 두고 각 막을 스토리 한 화로 연출한다(막 시작·끝과 보스 전 짧은 대화). 텍스트와 번역이 늘어난다.
- 도트 SRPG 분위기와 UI(잠정): 해상도 목업(RUNE-42)과 아트 방향에 반영한다.

## 합성과 등급
**합성은 두 갈래다.** (1) 승급: 같은 것 3개 → 1개(2개 승급은 없다). (2) 조합식: 서로 다른 재료 2~3개 → 새로운 하나(고정 레시피표).
- 대상은 유닛과 카드. 승급은 이름과 단계가 모두 같은 3개만 합쳐진다(다른 단계·다른 이름은 승급 재료로 섞이지 않는다).
- 단계는 1→2→3 (유닛은 ★1~★3, 카드는 Lv1~Lv3). 3단계가 최대이며, 최대까지 가려면 같은 것 9개가 필요하다.
- 합성 결과는 능력치·효과가 오르지만 **등급(희귀도)은 바뀌지 않는다.** 단계와 등급은 별개 축이다. 승급 보상은 「방향」 절의 정의(외형 변화 + 직업 카드 1장 + HP·방어 상승)를 따른다.
- 합성 시점은 야영지와 상점 전후의 정리 화면이다. '합성 가능'이 표시되면 플레이어가 직접 확정한다(자동 아님, 잠정, M4 시험).
- 조합식(2026-10-21 결정): 대상은 유닛과 카드(유물 제외). 서로 다른 재료 2~3개 → 새 이름의 하나이며 고정 레시피표로 관리한다. 일부 레시피는 처음부터 보이고 나머지는 발견하면 도감에 기록한다. 결과는 재료 단계와 무관하게 항상 ★1(Lv1)로 시작하고, 그 뒤 같은 이름 3개 승급은 기존 규칙을 따른다. 같은 것 3개를 모으기 어렵다는 위험의 두 번째 길이기도 하다.
- 유물은 합성하지 않는다.

**등급(희귀도) — 유닛·카드·유물 공통, 4단계**
| 등급 | 색 | 비고 |
|---|---|---|
| 일반 (Common) | 회색 | 가장 흔함, 합성 재료의 주류 |
| 고급 (Uncommon) | 초록 | |
| 희귀 (Rare) | 파랑 | 빌드 핵심 |
| 전설 (Legendary) | 주황 | 보스·특수 보상 위주, 한 판에 1개 안팎 |
유물은 이에 더해 보스 유물과 저주 유물 분류를 둔다. 등급별 출현 확률과 가격은 M3 에서 정한다.

**미결:** 전설 유닛 존재 여부 · 합성 단계별 능력치 증가폭 · 조합식 레시피 개수와 구성 · 대기석 6칸의 적정성(M3 실측).
**합성 빈도:** 3개 합성은 한 판 안에서 같은 것을 3개 모으기 어렵다. 풀을 작게 유지하고, 이미 가진 것이 나올 확률을 높이고, 상점에서 고르거나 살 수 있게 한다. M4 에서 실측한다.

## 직업 (MVP 4종)
기사(방어·도발) · 레인저(원거리·위치) · 마법사(원소 조합) · 성직자(회복·정화). 추후 도적·소환사.

## 한 판
목표 30~45분(숙련자 기준, 처음 하는 사람은 더 길다. 전투 N분 × 전투 수 예산식은 M3 실측으로 정한다). 메타 성장은 직업·유물 해금과 난이도 단계.
노드 수는 잠정이다. 격자 전투는 한 판이 슬레이 더 스파이어보다 길어서(전투 3~4분이면 3막 × 12노드는 목표 시간에 안 들어간다) 막당 8~10노드로 줄이거나 전투를 짧게 만든다. M3 시험 플레이에서 실제 시간을 재서 정한다.

## 아트 방향
**2D 도트(픽셀아트), 움직임은 최소.** 턴제라 큰 애니메이션이 필요 없고, 제작 비용과 에셋 수를 줄이는 방향이다.
- 기준 해상도 **640×360**(잠정, 2026-10-21 목업 결과), 정수 배율(×3 = 1080p, ×4 = 1440p, ×6 = 4K)로 확대한다. 타일은 **32×32**(잠정)이며
  무료 에셋 조사(RUNE-20)에서 32px 팩이 충분한지 확인한 뒤 확정한다. Steam Deck(1280×800)은 ×2 = 1280×720 으로 가로를 꽉 채우고 위아래에 여백이 남는다.
  근거와 한계는 docs/resolution-mockup.md.
- 유닛 스프라이트는 대기 2~4프레임이 기본이다. 공격·피격·이동은 별도 프레임 대신 위치 이동(트윈), 흰색 번쩍임,
  화면 흔들림, 간단한 파티클로 표현한다.
- **캐릭터·몬스터의 움직임은 최소로 한다.** 걷기·달리기 프레임은 만들지 않는다. 타일 이동은 대기 프레임 그대로 칸 사이를 미끄러지듯 옮기고,
  공격은 앞으로 살짝 내딛었다 돌아오는 트윈, 피격은 흰색 번쩍임과 밀림, 사망은 페이드아웃으로 처리한다. 직업·몬스터당 필요한 그림은 대기 2~4프레임이 전부다.
- 카드·유물은 정지 아이콘(예: 32×32)으로 제작한다. 일러스트 풀 컷은 쓰지 않는다.
- 직업 4종 × 단계 3(★ 표시는 장식·색조 변화로 구분) 규모로 스프라이트 수를 통제한다.
- 도구 후보는 Aseprite(유료)와 무료 대안(LibreSprite, Pixelorama). 가격·라이선스는 도입 시점에 URL 과 확인일을 남긴다.
- 에셋 라이선스는 받을 때 출처 URL·확인일을 기록한다.

## 목표 플랫폼
Steam 출시용 네이티브 PC 게임(Windows 우선, Steam Deck 고려). 웹 게임이 아니다.
Steamworks 연동(업적·클라우드 저장·Steam 입력)과 Steam 상점 요건(캡슐 이미지·트레일러)이 필요하다.

## 기술안
- **엔진: Godot 4 확정**(2026-10-20 사용자 결정). 정확한 버전과 다운로드 URL 은 설치 시점에 공식 사이트에서 확인하고 이 문서에 확인일과 함께 남긴다.
  **설치 기록(2026-10-21):** `4.7.2.stable.official.ed1daf0bf`, 맥 사용자 폴더 `~/tools/godot/4.7.2`, 출처 https://github.com/godotengine/godot-builds/releases/tag/4.7.2-stable, `Godot_v4.7.2-stable_macos.universal.zip` 의 SHA-512 가 같은 릴리스의 `SHA512-SUMS.txt` 와 일치(별도 서명은 확인하지 않음).
- Steam 연동은 GodotSteam, 시험은 GUT 또는 GdUnit4, 언어는 GDScript(C# 은 .NET SDK 가 필요해 보류).
- **규칙 엔진은 렌더링과 분리**한다. 엔진 API 에 기대지 않는 순수 코드, 시드 고정 난수, 결정론적 시뮬레이션,
  화면 없이 헤드리스 시험으로 전투·합성·유물 규칙을 검증한다.
- 아트는 2D 도트(위 「아트 방향」). 개발 초기에는 임시 도형으로 시작한다.
  이진 에셋이 늘면 git LFS 도입을 검토한다.

## 개발 환경
- 원격 저장소: GitHub `Jaewon94/runefold`(비공개). **M0 는 맥에서 로컬 Godot 로 시작한다**(2026-10-21 결정). Home1 `game-dev` 는 상시 가동 환경이 준비되면 합류한다.
- 개발 환경은 Home1 의 **게임 전용 Windows 일반 계정 `game`**(관리자 아님)과 그 전용 WSL `game-dev`(Ubuntu 24.04)이다. WSL 은 Windows 드라이브 마운트와 interop 이 꺼져 있고 화면(DISPLAY)이 없다. Orca 서버, deploy key, 클론, Claude Code 설치까지 끝났고 현재 상태는 Confluence 「03 개발 환경」에 둔다.
- 임시로 Home1 의 다른 계정 WSL 에 작업 사본이 있다(정리 대상, 현황은 Confluence 03).
- 헤드리스 시험·Windows 내보내기는 처음에는 맥에서 하고(Godot 4.5 이후 Wine 불필요), Home1 `game-dev` 합류 뒤에는 WSL 에서도 한다. Windows 실행 확인은 Home1 모니터에서 하며, 내보낸 exe 를 모든 계정이 읽을 수 있는 폴더로 복사해 모니터에 로그인된 계정에서 실행한다.
- `game-dev` 의 WSL 은 마지막 `wsl.exe` 세션이 끝나고 15초 뒤 꺼진다(WSL 2.4.11.0). 상시 가동에는 관리자 예약 작업이 필요하다(RUNE-69, 보류).
- 회사 자료 경로는 건드리지 않는다. 시스템 설치 없이 사용자 폴더 안 포터블 실행 파일만 쓴다.

## 정본과 관리
- 이슈·문서의 정본은 **Jira `RUNE`(룬폴드)** 와 **Confluence `RUNE` 스페이스**이다(2026-10-20 생성). 이 문서는 Confluence 「01 게임 설계」의 사본이며, 어긋나면 Confluence 쪽이 맞다.
- Jira: 에픽 RUNE-1~7 이 마일스톤 M0~M6 에 대응한다. 흐름은 할 일 → 진행 중 → 완료.
- 참고 게임 분석(REA)은 요약 결론과 링크만 이쪽에 두고, 원본 기록과 상대 게임의 코드·에셋·디컴파일 출력은 올리지 않는다.

## 작업 규칙 (가벼운 버전)
- 브랜치는 `main` + 작업 브랜치. 커밋은 `<type>(<scope>): 한국어 요약`.
- 작업은 Jira `RUNE` 이슈 단위로 한다. 브랜치는 `<type>/RUNE-<n>-<slug>`, 커밋 본문에 `Refs RUNE-n`.
- 원격은 GitHub(비공개)이며 CI 는 GitHub Actions 로 M0 에서 구성한다(RUNE-43).
