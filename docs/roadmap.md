# Runefold 로드맵: 문서에서 출시까지 (v1, 2026-10-20)

게임 개발 경험이 없는 1인이 AI 코딩 에이전트와 함께 Steam 출시까지 가는 큰 그림이다. 정본은 Confluence 04(page 8552481)이고 이 파일은
사본이다(마지막 동기화 2026-10-21). v0 을 만든 뒤 Fable(모델)에게 문서만 주고 독립 검토를 시켰고, 그 지적을 확인해 v1 에 반영했다(11절 참조). 같은 날 3개 관점의 두 번째 검토도 반영했다(14절).
**일정 숫자는 출처 있는 통계가 아니라 사례에서 읽은 내 추정**이며 그렇게 표시했다. 확인하지 못한 것은 "미확인"으로 남겼다.

## 0. 용어 (처음 보는 말)

| 말 | 뜻 |
|---|---|
| 마일스톤(M0~M6) | 큰 작업 덩어리. 각각 "끝났다"고 말할 기준이 있다 |
| G0 | 종이 프로토타입 판정. 규칙이 막힘 없이 돌고 억울함이 적은지 보는 관문(코드 전) |
| 재미 확인 관문(G1~G3) | 다음 단계로 가기 전에 "정말 재밌는가"를 사람이 확인하는 지점. 통과 못 하면 규칙을 바꾸거나 뺀다 |
| 종이 프로토타입 | 코드 없이 종이·토큰·손으로 쓴 카드로 규칙을 시험해 보는 것 |
| 프로토타입 | 재미를 확인하려고 거칠게 만든 시험판. 버려도 되는 것 |
| 수직 슬라이스 | 게임 한 판을 처음부터 끝까지, 품질은 낮아도 전부 이어서 돌려 본 것 |
| 알파 / 베타 | 알파=기능이 다 들어갔지만 거칠다. 베타=내용이 다 들어갔고 균형·버그를 잡는 중 |
| 데모 | 무료 체험판. 본 게임과 별도 앱으로 Steam 에 올린다 |
| Next Fest | Valve 가 연 3회(2·6·10월) 여는 데모 행사 |
| Steam Playtest | Steam 의 무료 비공개 시험 플레이 기능. 키로도 배포할 수 있다 |
| 위시리스트 | Steam 이용자가 "나중에 살 게임"으로 찜하는 것. 출시 알림이 간다 |
| Coming Soon 페이지 | 출시 전에 먼저 여는 상점 페이지 |
| 빌드 / SteamPipe | 실행 파일 묶음 / 그것을 Steam 에 올리는 도구 |
| GodotSteam | Godot 에서 Steam 기능(업적·클라우드 저장·입력)을 쓰게 해 주는 플러그인 |
| 헤드리스 시험 | 화면 없이 규칙만 자동으로 검사하는 시험 |
| CI | 코드를 올릴 때마다 시험을 자동으로 돌리는 장치(GitHub Actions) |

## 1. 한 장 요약

```
사전 검증 → M0 → M1 ─G1→ M2 ─G2→ M3 → M4 ─G3→ M5 슬라이스 → M5a 콘텐츠 완성 → M5b Steam 뼈대 → M5.5 데모·Next Fest → M5.9 안정화 → M6 출시 심사 → 출시
(종이·목업)                  ↑ G2 통과 직후 Steamworks 가입                ↑ 공개 상점 페이지·Playtest·SteamPipe가 데모의 전제
```

- 재미 확인 관문 3개: G1(M1 끝), G2(M2 끝), G3(M4 끝). 가장 위험한 가정(3→1 합성)은 G3 에서 확인한다.
- 코드 전에 **종이 프로토타입(1~2일)** 과 **해상도 목업(반나절)** 을 먼저 한다.
- 보정 전 합계 약 **77~113주**: 2026-10-21 기점 종료일 **2028-04~2028-12**(날짜 계산 확인). ×1.5 보정(근거 없음, M0~M1 병목 기록 RUNE-45 후 실측 배율로 교체)을 하면 116~170주, 즉 **2029-01~2030-01**.
  이 숫자는 "주 20시간 사람 개발" 모형의 산출물이며 AI 상시 가동 모형으로는 다시 뽑지 않았다. Next Fest 는 연 3회라 한 회차를 놓치면 약 4개월 밀린다(±4개월).
  v0 의 "2028년 5~11월"은 콘텐츠 완성·Steam 뼈대·안정화 단계가 빠진 낙관이었다.
- 일정은 M0~M1 을 해 본 뒤 다시 추정한다. G2 를 통과 못 하면 전체가 바뀐다.
- 그림·소리: 무료 에셋으로 먼저 만들고 괜찮으면 출시 전에 교체(사용자 결정 2026-10-20).
- 개발 장소: M0 는 맥 로컬 Godot 로 시작하고 Home1 `game-dev` 는 상시 가동이 준비되면 합류(2026-10-21 결정).

## 2. 지금 확정된 것과 가정

확정(결정 장부 참조): Steam 네이티브 PC 게임, Godot 4, 승급은 같은 것 3개→1개(단계 1~3)이고 조합식은 잠정이며, 도트 2D 움직임 최소,
정본은 Jira·Confluence, GitHub **공개** 저장소(2026-10-22 전환, DEC46), 영어 우선+한국어 포함, 무료 에셋 먼저.

가정(틀리면 일정이 바뀐다):
1. 개발은 AI 에이전트가 거의 상시 돌아간다(사용자 답 "거의 24시간", 해석 — 틀리면 정정). 병목은 코딩 시간이 아니라 **사용자의
   결정·플레이테스트·검증·계정/서류/결제**와 **AI 사용 한도·비용**이다. 3절의 기간은 "주 20시간 개발" 가정으로 잡은 것이라
   모델이 일관되지 않다. 코딩 위주 단계(M0~M2, M4 규칙 구현)는 줄 수 있지만 관문·플레이테스트·콘텐츠 제작·균형 조정은 줄지 않는다.
   줄어드는 폭은 근거가 없으므로 M0~M1 의 병목 기록(RUNE-45)으로 다시 추정한다.
   AI 사용 한도: Pro·Max 모두 5시간 + 주간 한도가 있고 Claude 앱과 Claude Code 가 한도를 공유하며, 초과분은 기다리거나 API 요금으로 추가 과금한다(공식 지원 문서, 확인일 2026-10-21). 구독만으로 24시간 가동은 성립하지 않으며 월 예산 상한은 미정이다.
2. 사용자는 결정·플레이테스트·계정/서류/결제를 맡는다. 주당 개입 시간은 미정.
3. 출시 마감은 없다("다 되면", 해석). 품질 우선.

## 3. 단계별 계획

기간은 모두 내 추정이다(출처 없음). 비슷한 사례의 개발 기간과 "첫 개발 일정은 늘어난다"는 경험칙에서 잡았다.

### 단계 A. 사전 검증 (지금~약 2~3주)
- 할 일: Home1 환경 마무리(RUNE-12), 1페이지 설계서(RUNE-13), **이름·상표 조회와 이름 확정(RUNE-34, RUNE-36)**,
  **종이 프로토타입(RUNE-41)**, **해상도 목업(RUNE-42)**, 콘텐츠 예산표(RUNE-44), 저장 시점·되돌리기 범위(RUNE-46),
  합성 빈도 계산(RUNE-24, 스프레드시트/간단한 몬테카를로, 코드 작성 승인 필요).
- **종이 프로토타입**: 8×8 격자, 아군 토큰 4개, 손으로 쓴 카드 20장으로 3판. 규칙·카드·시나리오·판정 기준은 [paper-prototype.md](paper-prototype.md).
  M1 전 결정은 2026-10-21 에 사용자가 정했고(설계서 「M1 전 결정」), 명중·사망 조합을 먼저 검증한다.
- **해상도 목업(완료, 2026-10-21)**: 480×270·640×360 에 손패 5장+격자+한글 설명을 놓고 비교했다([resolution-mockup.md](resolution-mockup.md)). 결과: 640×360 + 타일 32px 잠정. 기준 해상도는
  되돌리기 어려우므로 M0 에서 확정한다(Deck 은 화면에 표시되는 가장 작은 글자 높이가 1280×800 에서 9px 이상이어야 Verified, 공식).
- 끝났다는 기준: 새 클론으로 어디서든 시험이 도는 환경, 설계서에 「M1 전 결정」이 숫자로 적혀 있다.

**M1 전 결정 — 2026-10-21 사용자가 정했다(설계서 「M1 전 결정」). 아래는 원래 비어 있던 질문 목록**
1. 격자: 정확한 크기·가변 여부, 대각 이동, 지형 종류. 고저차는 탑다운 도트에서 표현이 어렵다(Into the Breach 도 없음)—넣을지 판단.
2. 턴 구조: 팀 턴(아군 전원→적 전원) vs 개별 순서, 이동→행동 순서, 이동 취소 범위.
3. 명중 방식: 확률(XCOM) vs 확정(Into the Breach). 적 행동 예고·결정론과 맞물린다.
4. 유닛 스탯 집합(HP·이동·사거리·공격·방어)과 적 1종의 행동 규칙.
5. 승패·사망: 전멸만 패배인가, 사망 유닛은 영구 손실인가(★ 유닛 손실은 합성 체감에 직결).

**M2 전 결정**: **덱 소유 모델**(유닛별 덱 vs 소대 공유 덱+직업 태그, 손패 5장이 소대 전체 한 손인지, 카드를 내면 어느 유닛이
실행하는지, 죽은 유닛의 카드, "같은 카드 3장" 합성의 모집단). 에너지 3·드로우 5·덱 크기·턴 종료 시 폐기·환급 상한. 상태효과 어휘.
**M3 전**: 대기석 수, 노드 타입, 유물 형태(장착형 vs 런 전역). **M4 전**: 단계별 배수, 자동/수동, 전설 유닛, 합성 시 덱 축소 보정.

### 단계 B. M0 뼈대 (RUNE-1, 약 3~4주)
- 할 일: Godot 4.7.2 포터블 설치, 폴더 구조, 규칙 코어/화면 분리, GUT 헤드리스 시험, 시드 고정 난수, Windows exe 내보내기,
  모니터 PC 실행 경로, **CI(GitHub Actions)에서 헤드리스 시험 통과를 병합 조건으로(RUNE-43)**, 무료 에셋 라이선스 대장.
- 끝났다는 기준: 시험이 `godot --headless` 로 통과(종료 코드 0), CI 가 병합을 막는다, exe 가 모니터 PC 에서 뜬다, 해상도 확정.
- M0 4주 동안 결정 요청 수·대기 시간·AI 사용량을 기록한다(RUNE-45).
- GodotSteam 호환 시험은 M0 에서 빼고 M5b 로 옮겼다(M2 전에는 가치가 없고 버전이 자주 바뀐다).

### 단계 C. M1 격자·이동·적 1종 (RUNE-2, 약 4~6주)
- 끝났다는 기준: 한 방에서 이동·공격·피격이 규칙대로 돌고 핵심 규칙에 자동 시험이 있다.
- **G1 재미 관문(RUNE-21):** 이 단계만으로 10분 내내 흥미로운 결정이 있는가(사용자가 직접 플레이).

### 단계 D. M2 카드·에너지·적 AI (RUNE-3, 약 6~8주)
- 끝났다는 기준: 카드 20~30장으로 전투 한 판이 승패까지 간다. 적이 다음 행동을 예고한다. 자동 대전으로 승률을 뽑을 수 있다.
  **UX 최소 요구(RUNE-47)**: 사거리 미리보기, 적 턴 건너뛰기, 되돌리기. **입력 추상화(RUNE-48)**: 마우스·키보드·패드가 같은 액션을 쓴다.
- **G2 재미 관문(RUNE-22):** 지인 3명이 설명 없이 한 전투를 끝내고 "한 번 더"를 말하는가.
- M2 직후 **합성 조기 시험(RUNE-74)**: 지도·상점 없이 정해진 보상 순서로 승급·조합식이 재밌는지 먼저 본다. G3 의 사전 신호이며 M4 설계를 바꿀 수 있다.
- G2 통과 시: 핵심 규칙(에너지·카드·격자) 고정, **Steamworks 가입 시작(RUNE-37)**, **외부 검증 전진(RUNE-75)**: 무료 웹 프로토타입(itch) 또는 Steam Playtest(키 방식, 공개 상점 페이지 불필요)로 낯선 사람 5~10명에게 보인다.

### 단계 E. M3 지도·상점·유물 (RUNE-4, 약 8~10주)
- 끝났다는 기준: 1막 한 판 완주(유물 8~10종). **한 판 길이 실측(RUNE-23)** → 막 수·노드 수 결정. **오디오 뼈대(RUNE-49)**.

### 단계 F. M4 합성 (RUNE-5, 약 8~12주)
- 합성은 두 갈래다: **승급**(같은 것 3개 → 1개)과 **조합식**(서로 다른 재료 2~3개 → 새것, 고정 레시피표, 유닛·카드 대상, 결과 ★1 시작,
  일부 레시피는 처음부터 보이고 나머지는 발견 시 도감에 기록). 조합식은 범위를 키우지만 "같은 것 3개를 모으기 어렵다"는 위험의 두 번째 길이다.
  레시피표 설계(RUNE-67)와 도감 UI(RUNE-68)가 추가됐다. 일정은 승급만일 때(6~8주)보다 2~4주 늘려 잡았다.
- 끝났다는 기준: 승급·조합식이 규칙·화면(야영)·시뮬레이션에 모두 반영. 합성 있는/없는 버전을 비교한 결과가 기록됨.
  합성으로 카드가 줄어드는 문제(3→1)를 자동 대전으로 점검.
- **G3 재미 관문(RUNE-25, 가장 중요):** 합성이 결정을 더 재밌게 하는가. 아니면 규칙을 바꾸거나 뺀다. 뺀다면 차별점이 사라지므로
  설계를 다시 보는 지점이다. 통과하면 합성 규칙 고정.

### 단계 G. M5 수직 슬라이스 (RUNE-6, 약 12~16주)
- 직업 4, 유물 30, 보스 1, 저장. 1막 완주 + **설정 메뉴·패드로 완주·로그 파일·빌드 번호 표시(RUNE-50)**.
- 끝났다는 기준: 처음부터 끝까지 완주, 지인 5명 이상 플레이테스트, 한 판 30~45분 측정. 이 시점부터 **기능 추가 금지**(RUNE-26).

### 단계 G2. M5a 콘텐츠 완성 / 알파 (RUNE-38, 약 12~20주, 신설)
- 2·3막, 보스 2~3, 적 전량, 엘리트·이벤트 방(RUNE-52), 직업별 카드·유물 전량(RUNE-53), 해금(RUNE-54),
  **튜토리얼·온보딩(RUNE-55)**, 업적 목록(RUNE-56), 크레딧·라이선스 고지와 AI 사용 대장(RUNE-57).
- 끝났다는 기준: 처음부터 끝까지 전 막 완주 가능, 콘텐츠 예산표의 수량 달성.

### 단계 G3. M5b Steam 뼈대 (RUNE-39, 약 4~6주, M5a 와 일부 병행, 신설)
- Steam 앱 생성과 SteamPipe 비공개 빌드 업로드(RUNE-59), **Steam Playtest 로 낯선 사람 10~30명(RUNE-60)**,
  상점 자료(캡슐·스크린샷·트레일러, 비아티스트에게 2~4주 추정, RUNE-61), Coming Soon 페이지 공개(RUNE-31), GodotSteam 기본 초기화(RUNE-62).

### 에셋 전략 (그림·소리)

1. **임시 도형 → 무료 에셋 → 출시 전 교체**의 3단계. M0~M2 는 도형이나 최소 그림으로 충분하다.
2. 교체 가능한 구조: 카드·유닛·유물 데이터가 스프라이트/소리 **경로만 참조**하게 한다.
3. 무료 에셋은 **상업 이용이 가능한 라이선스(CC0 등)만**. 비영리(NC)는 피한다. CC-BY·OFL 폰트처럼 표기 의무가 있는 것은 크레딧 화면(RUNE-57)에
   넣는다. 받을 때마다 출처 URL·라이선스·작가·확인일을 대장에 적는다.
4. 타일 32px, 640×360 규격에 맞는 팩을 고른다(32px 무료 에셋이 충분한지 먼저 확인한다).
5. AI 생성 그림·소리, **AI 가 쓴 게임 내 텍스트·번역(카드 설명, 대사)** 도 Steam 콘텐츠 설문에 공개한다(공식 설문은 "게임에 담겨 플레이어가
   소비하는 콘텐츠"를 공개 대상으로 본다). 코드 보조는 효율 도구로 보여 공개 대상이 아니라는 해석이지만 출시 전 원문을 재확인한다.
6. 무료 에셋이 어디에 있고 어떤 조건인지는 조사하지 않았다(미확인). M0 때 후보의 라이선스를 직접 읽고 대장에 올린다(RUNE-20).
7. 출시 전 교체 범위는 G3 이후 정한다. 재밌다고 확인된 뒤에만 그림·소리에 돈과 시간을 쓴다.
8. 무인(상시) 개발의 안전장치: 에이전트는 작업 브랜치에서만 일하고, **CI 의 시험 통과가 병합 조건**이며(RUNE-43), 외부에 보이는 작업
   (Jira·Confluence·GitHub 설정·결제)은 사람 승인 뒤에 한다. "설명할 수 있는 코드만 병합"은 비개발자가 지키기 어려우므로
   병합 기준을 "시험+시드 재현+사용자 플레이 확인"으로 한다.

## 4. 기술 기준 (M0 에서 정할 것과 권장값)

| 결정 | 권장 | 근거/비고 |
